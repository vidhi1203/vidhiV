STL & MSTL: anomaly detection with seasonality

November 2025 12 min read
Anomaly Detection Time Series ML

Time series anomaly detection has some really solid, statistically grounded techniques — like z-score and interquartile ranges (IQR). They're cheap, easy to implement, and often surprisingly effective. But sometimes we need more. Especially when our data has seasonality, trends, or both.

The problem with z-score on seasonal data

Imagine we're tracking the number of users on an office network. Every morning, employees log in — usage goes up. After work hours, people log off — usage drops. This gives us a very clear daily rise and fall pattern.

Now apply z-score to this data. There are two failure modes:

  • Too low threshold (e.g. z = 1) — way too many false positives, flagging anything above the daily peaks.
  • Too high threshold (e.g. z = 2) — things look clean until there's a cyber attack during the night. The attack looks "normal" compared to daytime usage, so z-score misses it entirely.

Z-score isn't "bad" — it's context-blind. Once your data has structure (like daily patterns), a single global threshold struggles. Too low → everything is an anomaly. Too high → real problems slip through. This is where statistical methods start to break down.

Enter STL: Seasonal-Trend decomposition using LOESS

STL breaks a time series into three components:

Xt = St + Tt + Rt

Where:

  • Xt = observed value at time t
  • St = seasonality (daily, weekly, etc.)
  • Tt = trend (long-term movement)
  • Rt = residual (what's left)

STL uses LOESS (Locally Estimated Scatterplot Smoothing). Instead of fitting one global curve, LOESS fits local regressions around each timestamp using neighboring points. This makes STL local, adaptive, and robust to slow changes in patterns — exactly what we want for real-world time series.

The core STL API

from statsmodels.tsa.seasonal import STL

stl = STL(
    series,
    period=96,   # 15-min data: 1 day = 24 × 4 = 96 points
    robust=True  # downweight outliers during fitting
)
res = stl.fit()

The key parameters:

  • period — length of the repeating seasonal cycle in number of samples. Get this wrong and the residuals become misleading.
  • robust=True — STL iteratively downweights outliers so spikes don't distort the estimated seasonality/trend. Use this when you expect anomalies and don't want them becoming part of "normal."

Using the output

df["trend"]    = res.trend     # long-term movement
df["seasonal"] = res.seasonal  # repeating daily pattern
df["residual"] = res.resid     # where anomalies live

Now we combine STL with simple detection logic:

def stl_detect(df, value_col="value", period=96, k=3, robust=True):
    df = df.copy()
    res = STL(df[value_col], period=period, robust=robust).fit()
    df["residual"] = res.resid

    mu  = df["residual"].mean()
    sig = df["residual"].std()
    sig = sig if sig > 1e-12 else 1e-12

    # one-sided: flag positive spikes
    df["anomaly"] = df["residual"] > (mu + k * sig)
    return df

The idea is simple: decompose the series, then apply z-score on the residual. The residual is already cleaned of expected structure — so anomalies actually stand out.

Where STL works well — and where it starts to bend

STL is a very strong baseline when your data has one dominant seasonal cycle, shows slow smooth trends, and you care about deviations from expected behavior rather than raw values.

However, STL makes one important assumption: there is only one seasonal pattern that matters.

Real office behavior doesn't just repeat every day — it also follows a weekly rhythm. Weekdays are busy. Weekends are quiet. When we force STL to explain this entire structure using a single seasonal period, some weekly behavior leaks into the residual, or genuine anomalies on weekends become harder to distinguish from expected weekend behavior.

This isn't a failure of STL. It's simply a mismatch between the structure of the data and the assumptions of the model. So the natural question becomes: what if our time series has more than one seasonality?

MSTL: stepping it up

MSTL (Multiple Seasonal-Trend decomposition) extends STL by allowing multiple seasonal cycles. For our network example:

  • Daily seasonality: 96 points
  • Weekly seasonality: 96 × 7 = 672 points
from statsmodels.tsa.seasonal import MSTL

def mstl_detect(df, value_col="value", periods=(96, 672), k=3):
    df = df.copy()
    res = MSTL(df[value_col], periods=list(periods)).fit()

    df["trend"]    = res.trend
    # MSTL returns multiple seasonal components — sum them
    df["seasonal"] = res.seasonal.sum(axis=1)
    df["residual"] = res.resid

    mu    = df["residual"].mean()
    sigma = df["residual"].std()
    sigma = sigma if sigma > 1e-12 else 1e-12

    df["anomaly"] = df["residual"] > (mu + k * sigma)
    return df

Now the model expects weekends to look different. A sudden spike on a Sunday night becomes genuinely unexpected — so it pops out in the residual and gets flagged cleanly. This is the real value of MSTL: not "more math," but better expectations.

Final thoughts

If there's one takeaway from all of this: anomaly detection isn't about finding extreme values. It's about finding unexpected behavior.

STL answers a better question than z-score: "What should this value look like at this moment?" MSTL takes this one step further — acknowledging that most real systems have more than one rhythm.

The lesson isn't that you always need the fanciest model. It's that the best anomaly detector is the one that understands your data's structure. Start simple. Add structure when needed. And let anomalies live where they belong — in what your model didn't expect.
