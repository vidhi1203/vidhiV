Model context protocol

February 13, 2026 10 min read
MCP AI Infrastructure LLMs

Model Context Protocols, or MCPs, are pretty much what the name implies: protocols that help AI models access the context they need to perform tasks.

  • A model can be any language or AI model.
  • Context includes the external information or tools a model depends on to do meaningful work.
  • A protocol defines the rules for how this information is shared and accessed.

Put simply, MCPs allow AI models to connect with real-world data and tools in a structured and reliable way.

The brain analogy

Let's understand MCP using an example from our own bodies.

In humans, the organ that processes information and makes decisions is the brain. It helps us understand what we see, hear, and smell. But can the brain actually see, hear, or smell on its own? No. It depends on sensory organs to gather information from the world.

Similarly, in AI systems:

  • The brain is like the model — performing reasoning and decision-making.
  • The sensory organs (eyes, ears, nose) are like context providers, giving the brain access to external information.
  • The nervous system and signaling rules act like the protocol, ensuring information is transmitted correctly between organs and the brain.

The brain is smart, but blind without the eyes and deaf without the ears. MCP plays a similar role for AI models — it connects intelligence to the outside world.

Another analogy: before USB-C, devices required many different cables. USB-C standardized how devices connect. MCP does something similar for AI systems — instead of every application inventing its own way to connect tools and data, MCP provides a standard way for models, tools, and data sources to communicate.

MCP Architecture

Three roles typically exist:

  • MCP Host — AI application that coordinates one or more MCP clients
  • MCP Client — Component that communicates with MCP servers
  • MCP Server — Service exposing tools, data, and prompts

The server provides context. Clients request it. Hosts orchestrate everything.

Core MCP Primitives

An MCP server exposes three main primitives:

1. Tools

Executable functions an AI system can call. Examples: database queries, file operations, API calls, running calculations. Tools perform actions.

2. Resources

Read-only data sources. Examples: file contents, database records, logs, API responses. Resources provide data, not actions.

3. Prompts

Reusable instruction templates. They guide how models should use tools and resources. Examples: system prompts, reasoning templates, structured workflows. Prompts help structure interactions.

Building a Small MCP Server

Let's build a small MCP server as a proof of concept. Our server will help track daily tasks, calendar events, and habits — using simple local files: a Markdown file for tasks, a CSV for habits, and an .ics calendar file for events.

Step 1 — Helper Functions

Before defining MCP tools, we create helper functions that isolate logic so multiple tools or prompts can reuse them.

# Tasks parsing — extract unfinished checklist items
def get_tasks():
    text = (DATA / "todo.md").read_text()
    tasks = []
    for line in text.splitlines():
        if "- [ ]" in line:
            tasks.append(line.split("- [ ]")[1].strip())
    return tasks

# Habit summary — check habits completed today
def habit_summary():
    df = pd.read_csv(DATA / "habits.csv")
    df.columns = [c.strip().lower() for c in df.columns]
    df["date"] = df["date"].astype(str).str.strip()
    today_rows = df[df["date"] == today_iso()]
    summary = {}
    for _, row in today_rows.iterrows():
        done = str(row.get("done", 0)).strip().lower() in {"1", "true"}
        summary[str(row["habit"]).strip()] = done
    return summary

Step 2 — Tools

Now we expose these as MCP tools:

@mcp.tool()
def next_tasks(n: int = 3):
    return get_tasks()[:n]

@mcp.tool()
def events_today():
    return get_events_today()

@mcp.tool()
def daily_brief():
    return {
        "tasks": next_tasks(),
        "events": events_today(),
        "habits": habit_summary()
    }

Step 3 — Prompts

Prompts guide how an AI system should use available tools:

@mcp.prompt("write_daily_summary")
def write_daily_summary(tone: str = 'friendly'):
    return f"""
Write a concise daily productivity summary.
Tone: {tone}
Steps:
1. Call events_today()
2. Call next_tasks(n=3)
3. Call daily_brief()
Output: Headline, bullet list of events, tasks, habit status.
Keep it actionable.
""".strip()

Step 4 — Resources

Resources expose data directly. Unlike tools, they don't perform computation — they provide content:

@mcp.resource("dashboard://todos")
def todos_resource():
    return (DATA / "todo.md").read_text()

@mcp.resource("dashboard://daily_brief")
def daily_brief_resource():
    return json.dumps(daily_brief(), indent=2)

Testing with MCP Inspector

Before connecting our server to more complex clients, we can use MCP Inspector — a tool designed specifically for testing MCP servers. It lets you view available tools, prompts, and resources, call tools manually, inspect outputs, and debug server behavior.

Launch it with:

npx @modelcontextprotocol/inspector

Open the local URL in your browser, set the transport type to STDIO, point it at your server.py, and click Connect. Inspector will display all exposed capabilities and let you test them interactively.

Wrapping Up

With just a few helper functions and decorators, we now have a fully working MCP server exposing tools, resources, and prompts. Even though this example uses simple local files, the same structure applies when connecting to real systems — databases, APIs, enterprise tools, or SaaS platforms.

The important takeaway: MCP is not about complexity. It is about standardizing how models access capabilities and context. If you can expose tools, resources, and prompts through MCP, you can plug your system into any MCP-compatible client or agent framework. And that is the real power of MCP.
